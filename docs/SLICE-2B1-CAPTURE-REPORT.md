# Slice 2B.1 — Real Chromium capture spike

Date: 2026-10-20. Status: continuous real Chromium → LiveKit → React demonstrated. Final 720p15 PASS at >=95% target; sustained fixed 720p30 FAIL. BrowserSession integration is deferred.

## Baseline and scope

Read Slice 0–1/2A reports, architecture, security boundaries, capture ADR, worker, publisher, generator, broker, React and Docker settings. Git is genuinely absent (`git rev-parse` fails). ## Architecture and real containers

Independent project zvonok-browser-capture: capture, guard, proxy, publisher, livekit, broker, rtc-relay, viewer. All eight were actually started. Headful Playwright Chromium → private Xvfb :91 → FFmpeg x11grab RGBA → existing 24-byte bounded raw IPC → RTC Node VP8/libvpx publisher → LiveKit → existing React RemoteVideoTrack/video. Dedicated app window excludes browser chrome. Playwright's default about:blank startup argument must be omitted, otherwise a second normal browser window is captured. There is no screenshot loop.

CDP candidate: local Page.startScreencast JPEG quality 90 → FFmpeg decode/scale/RGBA → same IPC/publisher. It has extra JPEG encode/decode and event cadence rather than an FPS guarantee. No public CDP/evaluate endpoint exists.

## Security

Own browser bridge 172.30.85.0/24, default-deny IPv4/IPv6 OUTPUT; only own restricted proxy 172.30.85.2:3128 allowed. Proxy has its own outbound bridge. Capture has only private frame and guard-marker volumes, no auth/key/control/socket/host mounts, no Docker socket. Publisher has private frame/auth sockets and its own trusted LiveKit namespace. Only broker/LiveKit mount the fresh experiment local key. No Core network membership. Host ports 47932 viewer, 47933 signaling and 47934 encrypted RTC relay bind loopback only.

Chromium UID1000, real namespace and Seccomp-BPF sandbox, no --no-sandbox. cap_drop ALL, read-only filesystem, no-new-privileges, original seccomp profile. Capture limits: 2 CPUs / 1024 MiB / 256 PIDs, shm 256 MiB, tmpfs 512 MiB. Xvfb TCP disabled and Xauthority cookie required; socket/profile/cookie exist only in private tmpfs, not published or shared. Display remains a privileged surface. Browser/capture share UID/container; trusted guard shares network namespace. This does not harden against a fully compromised same-UID browser accessing harness files, matching the original documented limitation.

Single experimental source/room only. Viewer token requires existing local-owner DEV_TOKEN and grants subscribe-only in unique slice-2b1-UUID room per broker epoch (initial comparison used a fixed experimental room). This is not BrowserSession ownership authorization and cannot be promoted to multi-session use. Fixed local Docker-exec command file has no public listener or arbitrary JS execution.

## Frames, bounds and stages

1280×720 CSS px/DPR1, raw RGBA, width/height/sequence/f64 frame-availability Unix ms in original header. Capture retains one assembling frame, one latest pending frame, one in-flight IPC; new pending frames replace old. FFmpeg pipes are bounded. CDP adds one pending JPEG/one decoder write. Existing publisher has one in-flight body/one latest frame. Not zero-copy: chunk assembly, publisher concatenation and native frame copies remain. FFmpeg conversion is before frame-availability timestamp and is not isolated by that header. FFmpeg filter/codec threads are explicitly one.

Experimental publisher logs capture-availability→submit and VideoFrame+captureFrame call cost; native aggregate encoding time is separate. It stops publication after two seconds without received frames, because the native source otherwise repeats old images. Automatic publisher restart is disabled to make failure explicit.

## Timing

Input-to-decoded-pixel: one Windows monotonic clock from before docker exec writes a fixed click/type command until requestVideoFrameCallback observes changed red/green pixels. Includes Docker command overhead, up to 50 ms harness file polling, browser input, capture, IPC, publication, delivery, decode and callback observation. It is a harness upper bound, not physical display scanout or a production API latency claim. Docker exec round trip is recorded separately and must not be subtracted, since it overlaps browser/capture work. Browser acknowledgment and IPC durations use Linux monotonic clocks separately. Existing React Unix-marker latency is uncalibrated across Windows/Docker/VM and is not reported as exact one-way latency. Native encoding and receiver decoding are aggregate per-frame means, not per-input stage timestamps.

## Reproduce

Build Dockerfile, Dockerfile.media, Dockerfile.guard, Dockerfile.viewer under experiments/capture using the four tags in compose.capture.yaml. A new ignored experiments/capture/livekit.local.yaml is generated from media/livekit.example.yaml with fresh random key and TCP/UDP 47934/47935. Never copy production keys. Dockerfile-specific ignore files exclude local keys. Start with docker --context desktop-linux compose -f compose.capture.yaml up -d. Viewer http://127.0.0.1:47932 accepts existing DEV_TOKEN.

MEDIA_FPS=15/30, CAPTURE_METHOD=x11/cdp; recreate capture and publisher together after stopping both. Run node experiments/capture/viewer-check.mjs with CAPTURE_SECONDS=65 and distinct CAPTURE_RUN. It saves decoded samples, input timing, Docker CPU/working-set/PIDs, per-process ps snapshots and viewer CPU-time/working-set snapshots. Source/publisher logs provide frame/drop/encode stages. Stop only this project with compose -f compose.capture.yaml down; no prune or volume deletion.

No publication/IPC protocol or original media source changed. This removes up to one pump period of avoidable waiting, retains one pending frame, and does not add an unbounded callback queue. At most one callback is scheduled. ## Functional and integration conclusion

The real-page continuous-video criterion is demonstrated, including click, text, animation, scroll, public example/Selenium form, navigation/back/forward/reload, sandbox and fail-closed egress. Initial API forward/reload 503 results remain FAIL in the original acceptance run; their cause is unresolved and was not concealed by changing original services.

The chosen private X11 pipeline is suitable for continuing this local spike; it is not approval for wide Worker migration. Fixed 720p30, precise product control latency, original BrowserSession authorization/DELETE/TTL wiring, resource headroom under a quiet repeatable host and pixel-perfect edge/crop validation are still gates for Slice 2B.2. Display/app geometry was logged (inner 1280x720, outer 1279x719); continuous text/orientation and marker position were visually/automatically checked, but one-pixel edge coverage was not separately validated. No scaling/crop correction is hidden.
